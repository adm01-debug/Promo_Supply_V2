
## Plan: Smoke test for date-fns subpath imports

### Context
A smoke test already exists at `src/test/dateFns.smoke.test.ts`, auto-generated by `scripts/generate-datefns-smoke-test.mjs` from actual `date-fns/<subpath>` imports under `src/`. It is wired into `scripts/ci-check.sh` (steps 8–9) and `scripts/ci-smoke.sh` (step 6), and `scripts/verify-datefns-files.mjs` checks the files exist on disk before the test runs.

What's missing: a single, fast, **standalone** developer command — no clean reinstall, no type-check, no report generation — that just regenerates the smoke test from current source and runs it. Useful when you've just added a new `date-fns/<subpath>` import and want a 5-second confirmation the pinned version actually ships that subpath.

### Change 1 — new `scripts/smoke-date-fns.sh`

Three steps, each echoed:

```bash
#!/usr/bin/env bash
# Quick standalone smoke test for date-fns subpath imports.
# Regenerates src/test/dateFns.smoke.test.ts from current src/ usage,
# verifies every imported subpath exists in node_modules/date-fns,
# then runs only the smoke test (no clean install, no tsc, no report).
#
# Usage: bash scripts/smoke-date-fns.sh
set -euo pipefail

echo "▶ [1/3] Regenerating smoke test from src/ imports..."
node scripts/generate-datefns-smoke-test.mjs

echo "▶ [2/3] Verifying date-fns subpath files exist on disk..."
node scripts/verify-datefns-files.mjs

echo "▶ [3/3] Running smoke test..."
exec npx vitest run src/test/dateFns.smoke.test.ts --reporter=verbose
```

Why these three steps:
- **Regenerate first** so the test reflects the *current* import surface, not whatever was committed. Catches "I added a new subpath import five minutes ago" cases.
- **File-existence check second** to fail fast with the clear "missing subpath file → reinstall" message before vitest produces a confusing module-resolution error.
- **`exec` on the final step** so the script's exit code is vitest's exit code — clean for CI/precommit reuse.

### Change 2 — `package.json` script entry

Add (idempotent — only if missing):
```json
"smoke:date-fns": "bash scripts/smoke-date-fns.sh"
```

So developers can run `bun run smoke:date-fns` (or `npm run smoke:date-fns`).

### Why this shape, not something else
- **Reuses existing tooling.** `generate-datefns-smoke-test.mjs`, `verify-datefns-files.mjs`, and `dateFns.smoke.test.ts` already exist, are battle-tested, and cover exactly what the user asked for (import every subpath, confirm it works on the pinned version). Building a parallel test would duplicate logic and create drift risk.
- **Standalone, not folded into `ci-smoke.sh`.** That script does a clean reinstall (~30s+); this one runs in ~2s. Different ergonomics, different use case.
- **Regenerates every run.** A stale committed test could pass while a newly-added import silently goes uncovered. Regenerating eliminates that gap.
- **No new test file.** The auto-generated `src/test/dateFns.smoke.test.ts` is the test — adding a hand-written second test would just diverge.

### Verification
1. `bash scripts/smoke-date-fns.sh` on current tree → all three steps green, vitest reports ~6 passing tests.
2. Add a throwaway `import { startOfDay } from "date-fns/startOfDay"` somewhere in `src/`, rerun → regenerated test includes `startOfDay`, still passes (subpath exists in 3.6.0). Revert.
3. Add a fake `import { notARealFn } from "date-fns/notARealFn"` → step 2 fails with "Missing date-fns subpath files: date-fns/notARealFn". Revert.
4. `bash scripts/ci-smoke.sh` and `bash scripts/ci-check.sh` → unchanged, still green.

### Risk / scope
- One new shell script (~15 lines). One `package.json` script entry. No source, dependency, route, schema, or existing-CI-script changes. Pure additive developer ergonomics on top of infrastructure that already exists.

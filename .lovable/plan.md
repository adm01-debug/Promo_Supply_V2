
## Plan: Emit dependency-health JSON from smoke test run

### Goal
Have the smoke test produce a small JSON report capturing the resolved `date-fns` versions (spec / locked / installed), alignment status, and a timestamp, saved to a file that CI can upload alongside existing smoke logs.

### Context
A broader `public/dependency-health.json` already exists, generated by `scripts/generate-dependency-health.mjs` (covers react/vite/typescript/shadcn/tree-shaking). This new report is **scoped to the smoke run** — a per-run snapshot, not the project-wide one — so it stays small, deterministic, and safe to overwrite per CI run.

### Output

**File**: `ci-logs/datefns-smoke-health.json` (sits next to existing `ci-logs/tsc-smoke.log` and `ci-logs/vitest-smoke.log`, picked up by the same artifact upload).

**Shape**:
```json
{
  "generatedAt": "2026-04-21T18:00:00.000Z",
  "source": "scripts/ci-smoke.sh",
  "dateFns": {
    "spec": "3.6.0",
    "specNormalized": "3.6.0",
    "locked": "3.6.0",
    "installed": "3.6.0",
    "exactPinned": true,
    "aligned": true
  },
  "lockfile": {
    "path": "bun.lock",
    "sha256": "abc123…",
    "sizeBytes": 12345
  },
  "smoke": {
    "tscExitCode": 0,
    "vitestExitCode": 0
  }
}
```

### Changes

#### 1. New file: `scripts/emit-smoke-health.mjs` (~70 lines)

Responsibilities:
- Reuse `scripts/lib/resolve-locked-version.mjs` (already used by `verify-datefns-versions.mjs` and `install-report.mjs`) — no new resolver logic.
- Read `package.json` spec, `bun.lock` resolved version, `node_modules/date-fns/package.json` installed version.
- Hash `bun.lock` (sha256, first 16 chars) + size — same convention as `install-report.mjs`.
- Accept `--tsc-exit <n> --vitest-exit <n>` CLI flags so `ci-smoke.sh` can pass through the captured `PIPESTATUS` values.
- Write to `ci-logs/datefns-smoke-health.json` (override path via `--out <path>`).
- Always exit 0 — this is a **report**, not a gate. The existing `verify-datefns-versions.mjs` and smoke test failures remain the actual gates.
- Print one-liner: `✓ Wrote ci-logs/datefns-smoke-health.json (aligned=true)`.

#### 2. `scripts/ci-smoke.sh` — invoke after smoke steps (~6 lines added)

After the existing `[7/7]` block that captures `SMOKE_TSC_EXIT` and `VITEST_EXIT`, add a final reporting step (numbering becomes `[8/8]`):
```bash
echo "▶ [8/8] Emitting dependency-health snapshot for smoke run..."
node scripts/emit-smoke-health.mjs \
  --tsc-exit "$SMOKE_TSC_EXIT" \
  --vitest-exit "$VITEST_EXIT" \
  --out "$LOG_DIR/datefns-smoke-health.json"
```
Runs even on green (after both exits are 0). On a red run, the script still emits the report before the earlier `exit "$VITEST_EXIT"` — so we move the emit step to run **before** the failure exits, capturing the failure mode in JSON. Concretely: split the existing `if [ "$SMOKE_TSC_EXIT" -ne 0 ]` and `if [ "$VITEST_EXIT" -ne 0 ]` blocks so the JSON is written first, then the script exits non-zero with the original code.

#### 3. `scripts/ci-check.sh` — same emit at the end (if it runs the smoke path)

Mirror the same `node scripts/emit-smoke-health.mjs …` call at the end of `ci-check.sh` so both entry points produce the artifact. Pass `0 0` for the exits since `ci-check.sh` aborts on failure earlier; if smoke logs exist there, capture their exits the same way.

#### 4. CI workflows — already covered

`.github/workflows/ci-check.yml` and `.github/workflows/datefns-smoke-drift.yml` already upload `ci-logs/**` as artifacts (existing `tsc-smoke.log` / `vitest-smoke.log` use the same dir). The new JSON file is included automatically — no workflow edits needed. Verify by reading the existing workflows; if either uploads a more specific glob (e.g. `ci-logs/*.log`), broaden it to `ci-logs/**`.

### What does NOT change
- `scripts/generate-dependency-health.mjs` / `public/dependency-health.json` — the project-wide snapshot stays as-is, on its own schedule.
- `scripts/verify-datefns-versions.mjs` — keeps its CI-gate role with distinct exit codes.
- `scripts/install-report.mjs` — keeps printing its human-readable table; the new JSON is the machine-readable counterpart.
- Any test files, generators, or `package.json` deps.

### Verification
1. Local green run: `bun run ci:smoke` → produces `ci-logs/datefns-smoke-health.json` with `aligned: true`, `tscExitCode: 0`, `vitestExitCode: 0`.
2. Force drift: edit `package.json` `date-fns` to `"3.5.0"` (without reinstalling) → JSON shows `aligned: false`, `installed: "3.6.0"`, `spec: "3.5.0"`.
3. Force tsc failure: break a smoke import → smoke fails, but JSON is still written first with `tscExitCode: 1`, then script exits non-zero.
4. CI: artifact `ci-check-smoke-logs` now contains the JSON next to the two `.log` files; downloadable from the PR's Actions tab.

### Risk / scope
- 1 new file (~70 lines), 2 small edits to existing shell scripts (~10 lines total), 0 deps, 0 test changes.
- Always-exit-0 design — never turns a green run red.
- File is overwritten per run — no stale data, no commits, no growth.
